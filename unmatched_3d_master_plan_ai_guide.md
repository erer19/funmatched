# Путівник проекту: Цифрова 3D-адаптація Unmatched (Master Plan & AI Guide)

> **Призначення документа:** Цей файл є одночасно **дорожньою картою для розробника (людини)** та **головним архітектурним путівником для ШІ-агента (Gemini в Google Antigravity)**. Він об'єднує найкращі практики з трьох базових концептів (`Plan 1`, `Plan 2`, `Plan 3`).

## 1. Суть проекту, межі MVP та інтелектуальна власність (IP)

Ми створюємо покрокову тактичну 3D-гру з картковою бойовою системою за мотивами настільної гри *Unmatched*. Замість важкого екшену з вільним пересуванням гра будується як **оживлений 3D-стіл** із фіксованою/орбітальною камерою, де мініатюри переміщуються між дискретними клітинками (просторами), а половина геймплею відбувається у зручному 2D-інтерфейсі карт.

### Обсяг першої версії (MVP):
* **Контент:** 1 ігрове поле (базова мапа), 2 герої зі своїми помічниками (sidekicks) та унікальними колодами по 30 карт.
* **Механіка:** Повний цикл ходу (2 дії з 3 можливих: **Маневр**, **Виверт/Задум**, **Атака**), реакція захисника, блокування шляхів чужими фігурками, ліміт руки в 7 карт та зменшення здоров'я до 0.
* **Режими гри на старті:** Локальна гра (Hot-Seat на одному ПК) + базовий ШІ-бот для соло-тестів. Онлайн-мультиплеєр виноситься на фінальний етап.

### Межі використання IP (Важливо для публікації):
* Для локального навчання й тестування архітектури можна використовувати механіки та персонажів із суспільного надбання (Король Артур, Медуза, Аліса, Сіндбад).
* Для публічного релізу (itch.io, Steam) **обов'язково** замініть назву гри, ілюстрації, точні тексти карт та ліцензованих героїв на власні, а також ведіть облік ліцензій усіх згенерованих ассетів у файлі `ASSETS.md`.
* Офіційний PDF правил використовуємо локально в папці `docs/` як довідник для агента, але не публікуємо у відкритому репозиторії.
* *(Детальніше про правила та юридичні межі див. у **Plan 2, розділ «Що відтворюємо: правила Unmatched і межі використання»** та **Plan 3, розділ 8**).*

## 2. Технологічний стек (Адаптовано під Antigravity та 4 ГБ VRAM)

Головний принцип роботи з Antigravity — **текстоцентричність**. Агент ідеально пише код, перевіряє та рефакторить проект, коли сцени, ресурси та дані збережені у текстових форматах (`.gd`, `.tscn`, `.tres`, `.json`), а не сховані у бінарних файлах. Крім того, стек оптимізовано під залізо з **4 ГБ відеопам'яті (VRAM)**.

## 3. Архітектура та Структура Проекту (Data-Driven + Headless Core)

**Золоте правило архітектури:** Ядро правил (`Game Core`) повністю відокремлене від 3D-графіки (`Presentation`) та інтерфейсу (`UI`). Модуль бою не знає про 3D-моделі, камери чи шейдери — він приймає **Команди** і повертає масив **Подій** для візуалізації.

### 3.1. Дерево директорій проекту (Godot)

### 3.2. Ключові підсистеми Data-Driven ядра
1. **Граф ігрового поля (`Map Graph`):** Візуально поле — це 3D-модель дошки, але для коду це JSON-граф. Кожна клітинка (`Space`) містить: `id`, 3D-координати `(x, y, z)` для постановки фігурки, масив сусідів `adjacentIds` та масив кольорових зон `zones` (для перевірки легальності атак дальнього бою). *(Детальніше див. у **Plan 1, Етап 2** та **Plan 3, Етап 2**).*
2. **Декларативна схема карт та тригерів (`JSON + Effect Resolver`):** Жодних гігантських `if-else` під кожну карту! Кожна карта в JSON має тип (`attack`, `defense`, `versatile`, `scheme`), базове значення, значення посилення (`boost`), прив'язку до персонажа (`character`: Hero / Sidekick / Any) та масив тригерів:
   * `IMMEDIATELY` — спрацьовує одразу при розкритті (наприклад, скасування тексту карти противника — *Feint / Виверт*);
   * `DURING_COMBAT` — модифікація сили карти, сліпе посилення (*Blind Boost*);
   * `AFTER_COMBAT` — переміщення бійців, добір карт, пряма шкода.
   *(Детальніше див. у **Plan 1, Етап 2**).*
3. **Детермінована State Machine, Команди та Події (`Commands -> Events`):**
   * Гравець, ШІ або мережа відправляють у ядро лише **Команди** (`ActionManeuver`, `ActionAttack`, `ActionScheme`, `PlayDefenseCard`).
   * Ядро валідує команду, оновлює `GameState` і видає масив **Подій** (`UnitMoved`, `CardPlayed`, `DamageDealt`, `HealthDialUpdated`), які 3D-сцена програє по черзі.
   * Усі перетасовки колоди використовують фіксований `seed`. Збереження `seed` + списку команд дозволяє за секунду відтворити будь-який баг. *(Детальніше див. у **Plan 1, Етап 2** та **Plan 2, Етап 2**).*

## 4. Покроковий Пайплайн Розробки (Етапи 0–8)

### Етап 0: Підготовка середовища, MCP та Документації
1. Ініціалізувати Git-репозиторій (налаштувати **Git LFS** для `*.glb`, `*.png`, `*.ogg`).
2. Встановити **Godot 4.7** та підключити до Antigravity MCP-сервери: **`godot-ai` (`godot-mcp`)** для керування сценами та **`blender-mcp`** для автоматизації 3D.
3. Покласти в `docs/` офіційний рулбук Unmatched.
4. Запустити **Перший (Bootstrap) запит в Antigravity** (див. Розділ 6 нижче), щоб агент згенерував стартові документи (`GDD.md`, `ARCHITECTURE.md`, `RULES_MODEL.md`, `AGENTS.md`) без написання ігрового коду.
*(Детальніше див. у **Plan 2, Етап 0** та **Plan 3, Етап 0 і Розділ 7**).*

### Етап 1: Headless-ядро правил та Юніт-тести
1. Реалізувати чисті класи `GameState`, `TurnManager`, `MovementRules`, `DeckManager`, `CombatResolver`, `EffectResolver` та `VictoryChecker`.
2. Описати JSON-дані для одного поля та двох базових героїв із простими ефектами (наприклад, *Король Артур* проти *Медузи*).
3. **Критична вимога:** Кожна механіка та кожна карта покриваються автоматизованими юніт-тестами (на базі прикладів із офіційного рулбука). Гра повинна вміти провести повний бій у консолі/тестах без жодної 3D-моделі.
*(Детальніше див. у **Plan 2, Етап 2** та **Plan 3, Етап 3**).*

### Етап 2: Фаза «Сірих коробок» (Greybox) та 3D-поле
1. Створити сцену `battlefield.tscn` із примітивів: площина столу, кружечки клітинок, з'єднані лініями, та прості кольорові циліндри/капсули замість героїв і помічників.
2. Налаштувати камеру з фіксованим кутом огляду над столом та м'яким орбітальним обертанням (з обмеженням кутів, щоб гравець не заглядав під стіл).
3. Підписати 3D-сцену на події з `GameState`, щоб циліндри пересувалися по клітинках згідно з правилами графа.
*(Детальніше див. у **Plan 1, Етап 5** та **Plan 3, Етап 2**).*

### Етап 3: Інтерфейс карт (UI) та Зворотний зв'язок
1. Створити UI-компонент карти (`Control`-ноди в Godot). **Важливий принцип:** ніколи не генерувати карту одним зображенням із текстом через ШІ! Генерується лише чиста ілюстрація, а рамка, іконка типу, числові значення атаки/бусту та текст ефектів збираються програмно з JSON. Це дозволяє міняти баланс за секунду.
2. Реалізувати віяло карт у руці, збільшення при наведенні (hover), підсвічування легальних клітинок для маневру чи атаки та 3D/2D лічильники здоров'я (Health Dials).
*(Детальніше див. у **Plan 1, Етап 4**, **Plan 2, Етап 5** та **Plan 3, Етап 4**).*

*Після завершення Етапу 3 ми маємо повністю іграбельний прототип. Далі Етапи 4, 5 та 6 можна вести паралельно.*

### Етап 4: Пайплайн 3D-моделей (2D → 3D → Blender MCP)
1. **Генерація 2D-референсу:** Згенерувати концепт фігурки в ізометрії або фронтально на білому фоні (ComfyUI з Flux/SDXL або Imagen 3).
   * *Рекомендований промпт з Plan 1:* `"unpainted grey plastic board game miniature, sculpted details, circular base, studio lighting, white background"`.
2. **Image-to-3D:** Перетворити картинку на `.glb` модель через **Tripo** (найкращий для персонажів) або **Meshy** (хороший для реквізиту), або локально/у хмарі через **Hunyuan3D-2 / TRELLIS**.
3. **Автоматизація в Blender (`blender-mcp`):** Попросити Gemini написати Python-скрипти (`bpy`) для Блендера, які:
   * генерують ідеально рівні круглі фішки помічників (sidekicks), коліщатка здоров'я та дошку;
   * автоматично чистять топологію згенерованих героїв (модифікатор *Decimate*), вирівнюють масштаб, прикріплюють стандартну підставку та експортують у `.glb`.
4. Записати джерело й тариф кожної моделі в `ASSETS.md`.
*(Детальніше див. у **Plan 1, Етап 3**, **Plan 2, Етап 3** та **Plan 3, Етап 5**).*

### Етап 5: Процедурний шейдер «Mini-Wash», Матеріали та Анімації
1. **Фірмовий шейдер «Mini-Wash» (замість ручного текстурування героїв):** Фізичні мініатюри Unmatched — це однотонний пластик із темною проливкою (wash) у заглибленнях. Запікаємо в Blender карту заглиблень (*Ambient Occlusion / Cavity map*), а Gemini пише кастомний шейдер у Godot (`.gdshader`), який бере базовий колір героя, затемнює западини (імітація акрилового вошу) і висвітлює гострі грані (імітація *drybrush*).
2. **Текстури оточення та ліміт VRAM:** Для столу й поля брати CC0 PBR-матеріали з **Poly Haven**, **ambientCG** або генерувати процедурно в **Material Maker**. Тримати роздільність текстур у межах **512px–2048px (1K–2K)** для стабільної роботи на 4 ГБ VRAM.
3. **Анімації настільних фігурок:** Не витрачати час на складний скелетний риг на старті. Реалізувати рух через `Tween` та `AnimationPlayer` у Godot: переліт фігурки по параболічній дузі при маневрі, різкий випад уперед при атаці, тряска й спалах при отриманні шкоди, частинки (`GPUParticles3D`) для ударів. *(Якщо пізніше знадобиться скелетна анімація для гуманоїдів — використати авто-ріг у **Mixamo** або **Meshy**).*
*(Детальніше див. у **Plan 1, Етап 4–5**, **Plan 2, Етап 4–5** та **Plan 3, Етап 6–7**).*

### Етап 6: Звук та Полірування
1. Створити в Godot `AudioManager` із трьома окремими шинами гучності: `Music`, `SFX`, `UI`.
2. Взяти базові звуки карт, кліків та ударів із **Kenney (CC0)** або **Freesound**, а фонову музику (2–3 треки: меню, бій, перемога) згенерувати через **ElevenLabs Music**, **Stable Audio 3** або **Beatoven.ai** (перевіривши комерційні права тарифу).
*(Детальніше див. у **Plan 2, Етап 6** та **Plan 3, Етап 9**).*

### Етап 7: ШІ-суперник (3 рівні) та Мережева гра
Завдяки ізольованому ядру з Етапу 1 і бот, і мережа працюють через одні й ті самі Команди:
1. **ШІ-бот (3 сходинки складності, як в офіційній Digital Edition):**
   * *Рівень 1 (Random):* Випадкова легальна дія (для швидких смоук-тестів).
   * *Рівень 2 (Greedy Heuristic):* Оцінка стану за формулою (різниця здоров'я, чи можна добити ворога, чи вигідно відступити, цінність карт у руці).
   * *Рівень 3 (Monte Carlo / Симуляції):* Оскільки `GameState` легкий і детермінований, бот може клонувати стан у пам'яті, підставляти випадкові карти у приховану руку ворога і проганяти сотні швидких симуляцій перед ходом.
2. **Мультиплеєр (фінальний крок):** Використовувати вбудований High-Level Multiplayer API (ENet) у Godot з **окремим авторитетним сервером** (екземпляр Godot у режимі `--headless`). Сервер тримає повний стан гри і надсилає кожному клієнту лише його власну руку карт, щоб унеможливити чітерство.
*(Детальніше див. у **Plan 2, Етап 7** та **Plan 3, Етап 8**).*

## 5. Інструкція з керування ШІ в Antigravity (Для `AGENTS.md` / `GEMINI.md`)

Щоб агент у Google Antigravity не ламав працюючий код і не губив контекст, зафіксуй у кореневому файлі `AGENTS.md` (та `GEMINI.md`) такі правила:

### 5.1. Жорсткі обмеження для Агента:
1. **Заборона змішування шарів:** Скрипти в `scripts/core/` НІКОЛИ не повинні імпортувати або залежати від візуальних вузлів (`Node3D`, `Control`, `AnimationPlayer`).
2. **Data-Driven підхід:** Нові карти та герої додаються через конфіги в `data/`, а не через хардкод у `combat_resolver.gd`.
3. **Малі ітерації та Докази роботи:** Одне завдання = один атомний Git-коміт. Після кожної зміни логіки агент зобов'язаний запустити юніт-тести. Після кожної зміни UI/3D агент зобов'язаний запустити сцену в Godot через MCP і надати скріншот (артефакт Antigravity).
4. **Заборона вигадування правил:** Якщо правило неоднозначне — звірятися з файлом у `docs/` та писати тест на конкретний кейс.

### 5.2. Модульні навички (`.agents/skills/`) та Субагенти
Коли базовий проект запрацює, попроси Antigravity створити 3 стандартизовані навички у `.agents/skills/`:
* `godot-gameplay` — стандарти написання GDScript, робота з сигналами та `GameState`.
* `blender-asset-pipeline` — скрипти пакетної оптимізації мешів, створення підставок та експорту `.glb`.
* `gameplay-testing` — запуск тестів правил і відтворення партій за `seed`.

При масштабуванні проекту розділяй роботу між спеціалізованими субагентами (**Gameplay Agent**, **Asset Agent**, **UI Agent**, **QA Agent**) в окремих Git-гілках або `git worktree`, щоб вони не перезаписували файли одне одного. *(Детальніше див. у **Plan 2, розділ «Ризики та поради»** та **Plan 3, Розділ 6**).*
